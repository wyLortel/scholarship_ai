# 작업 절차 — 시작·완료·변경 체크리스트

> 책임: **작업을 언제 시작하고 언제 완료라고 말하는가**, 규칙이 바뀌면 어디를 먼저 고치는가. 업무 규칙 자체는 `../01-domain/`, 수용 기준은 [`01-acceptance-tests.md`](01-acceptance-tests.md)가 원본이다. AI가 만든 코드도 예외 없이 이 절차를 따른다.

## 1. 시작 전 (Definition of Ready)

- [ ] 연결한 FR/ST/OP와 도메인 경로(A/B/C, D1~D4)를 적었다.
- [ ] 관련 BR과 수용 테스트 AC ID를 적었다(규칙 문장을 복사하지 말고 ID만).
- [ ] 공식 원문과 가상 fixture(`examples/`, TEST_ONLY)를 구분했다.
- [ ] 영향받는 API·상태·권한·최신성·버전 경계를 확인했다.
- [ ] 결정되지 않은 정책은 [`../00-governance/03-open-decisions.md`](../00-governance/03-open-decisions.md)에 OPEN으로 올렸다. **코드에서 임의로 결정하지 않는다.**
- [ ] 현재 저장소의 실제 구조·테스트 명령을 직접 확인했다(문서의 예시 구조를 그대로 가정하지 않음).

### 티켓 양식

```md
# [FR-… / ST-…] 사용자 가치가 드러나는 제목
- 왜: 업무 경로(A/B/C, D1~D4), 근거 EV-…
- 범위: Given / When / Then, Out of Scope
- 지킬 규칙(ID만): BR-…, 관련 ADR-…
- 모듈의 한 가지 책임 / 건드리지 않을 모듈 / API 계약
- 검증: AC-… (정상 + 모름·실패·구버전·권한·중복 요청)
- 미확정: OPEN-… (실행을 막는가, 안전한 임시 행동은?)
```

예: '소득 모름' 판정 → D2 / ST-02, ST-03 / BR-B01, BR-B03, BR-B04 / AC-B01, AC-B02. 책임은 `eligibility` 모듈이 사실 스냅샷과 검증 규칙 트리를 평가하는 것 하나. UI는 계산하지 않는다. 소득 기준연도·단위는 OPEN-02.

## 2. 완료 조건 (Definition of Done)

- [ ] 작동하는 최소 세로 슬라이스가 있고 API/UI/상태 책임이 분리됐다.
- [ ] 판정 규칙은 Rule Engine 한 곳에서만 계산한다(React/LLM/컨트롤러 중복 없음).
- [ ] 관련 P0 반례(UNKNOWN, 검증 전 공고, 구버전, 준비≠접수)가 테스트됐다.
- [ ] 학생 본인 자료 접근 제어와 로그의 비밀정보 노출을 확인했다.
- [ ] schema/API가 바뀌었으면 `contracts/`를, 중요한 기술 선택이면 새 ADR을 갱신했다.
- [ ] `python3 tools/check_pack.py`가 통과한다(문서·ID를 건드린 경우).
- [ ] 테스트·타입·린트·빌드를 **실행했거나, 실행하지 않았다고 명시**했다.
- [ ] PR은 작고 사람 1명 이상이 확인한다. AI는 승인자가 아니다.

### 완료 보고 양식

```text
변경 기능: FR-/ST-
근거한 규칙: BR-..., AC-...
변경 파일:
실행한 검증: 명령 / 결과 / 재현 방법
실행하지 못한 검증: ... (이유)
문서·계약·ADR 변경:
미해결: OPEN-...
```

**이런 완료 보고는 금지:** "Agent Server가 자동 복구를 지원하니 장애 테스트 완료", "프롬프트에 써놨으니 판정 정확", "초안 다운로드가 됐으니 신청 완료".

## 3. 무언가 바뀌었을 때 — 주인 문서를 먼저 고친다

| 바뀐 것 | 먼저 고칠 유일 원본 | 같이 확인할 곳 |
|---|---|---|
| 인터뷰 발언·공식 원문 추가 | `00-governance/01-evidence.md` | 도메인 스토리, PRD 문제 설명 |
| 공고 해석·자격 규칙 | 공식 원문 이력 + `01-domain/04-business-rules.md` / `05-eligibility-policy.md` | AC, fixture, API |
| 제품 범위·우선순위·구현 순서 | `02-product/01-PRD.md` | Out of Scope, 슬라이스 |
| 상태 의미 | `01-domain/06-state-machines.md` | DTO, DB, 테스트, UI |
| 수용 기준·FR↔AC 연결 | `04-delivery/01-acceptance-tests.md` | 코드 테스트 이름, fixture |
| 기술 구성·의존성 | 새 ADR (`Supersedes: ADR-nnnn`) | architecture, CI, contracts |
| API 필드 | `contracts/` (승인 후) | FE, BE, Agent, fixture |
| 테스트 통과 여부 | CI 로그·실행 증빙 | PR |

- 승인된 BR을 코드로 먼저 바꾸고 규칙을 뒤늦게 합리화하지 않는다: 변경 의도 → 근거 → 테스트 → 팀 승인 → 변경.
- 승인된 ADR의 맥락·결과를 덮어쓰지 않는다. 새 ADR에 바뀐 전제·대안·이주 계획을 쓰고 기존 ADR은 `SUPERSEDED`로 표시한다.

PR에 남길 최소 기록: 왜 바꿨나 / 기존 규칙·근거 ID / 새 관찰 / 대안과 손해 / 수정한 원본 문서 / 연쇄 영향(상태·API·데이터·테스트·보안) / 검증 결과 / 실행 못 한 위험.

## 4. 자주 쓰는 요청 문장

- **기술 선택 변경:** "관련 ADR을 읽고 현재 문제·요구 품질 수치·대안(2개 이상)·얻는 것·단점·롤백 조건·검증 실험을 표로 비교해. 수치가 없으면 추정으로 승인하지 말고 측정을 제안해. 결정이 바뀌면 새 ADR로."
- **코드 리뷰:** "이 변경이 [FR-/BR-/AC-]와 일치하는지 봐. 원문 검증·UNKNOWN·버전/근거·개인정보·준비/접수 분리·멱등성을 중점으로, 위반은 '문제/위험/재현/파일·라인/수정안/필요 테스트'로. 테스트를 돌리지 않았으면 통과라고 쓰지 마."
