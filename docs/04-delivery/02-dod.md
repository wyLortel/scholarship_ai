# 팀 완료의 정의 (DoD) — AI 생성 코드도 예외 없음

> 책임: **작업 완료를 언제 선언하는가**. 문서와 규칙을 다 읽었다는 이유만으로 기능 완료가 아니다.

## 티켓 시작 조건 (Definition of Ready)

- [ ] 연결된 제품 스토리(`ST/OP/FR`)와 도메인 경로(`A/B/C/D1~D4`)를 1개 이상 적었다.
- [ ] 공식 원문·가상 fixture 구분과 관련 BR 규칙을 적었다.
- [ ] 사용자가 기대하는 정상/오류/모름 결과와 수용 테스트 ID를 적었다.
- [ ] 필요한 API·상태/권한·예외·최신성·버전 경계를 확인했다.
- [ ] 불명확한 제품 정책은 `OPEN-ID`를 발행했다. **코드에서 임의로 결정하지 않았다.**

## 구현 완료 조건

- [ ] 작동하는 최소 세로 슬라이스가 있고 API/UI/상태의 책임이 분리되었다.
- [ ] 규칙을 Rule Engine 한 곳에서 계산하며, React/LLM/컨트롤러에 중복되지 않는다.
- [ ] `UNKNOWN`, 공고 검증 전, 구버전, 접수와 준비 경계 등 관련 P0 반례가 테스트됐다.
- [ ] 학생 본인 자료 접근 제어와 로그 비밀 정보 노출을 확인했다.
- [ ] schema/API 변경이 있으면 관련 `contracts/` 또는 기존 실제 계약을 갱신했다.
- [ ] ADR이 필요한 중요한 변경이면 맥락·대안·감수할 단점·검증을 기록했다.
- [ ] 문서·코드·테스트가 같은 용어를 쓴다. 임시 가정은 가정으로 표시한다.
- [ ] 테스트/타입 검사/린트/빌드를 **실행했거나 미실행을 명시**한다. 임의 성공 주장 금지.
- [ ] PR은 작고 리뷰 가능한 단위이며 최소 1명의 책임 있는 사람이 확인한다. AI는 승인자가 아니다.

## API/UI 병렬 개발을 위한 계약 점검

- enum, null/unknown, date·timezone, version, evidence ID, Idempotency-Key, 인증/오류 응답, 상태 복원이 합의되었는가?
- 실패했을 때 자동 retry 여부와 UI 문구가 같은가?
- fixture가 같은 데이터를 사용하고, 가짜 기관 공고를 실제 공고처럼 라벨링하지 않았는가?

## 작업 보고 템플릿

```text
기능/티켓: FR-/ST-
유지한 불변식: BR-...
변경 파일/기능: ...
실행한 검증: 명령, 성공/실패, 재현 방법
실행하지 못한 검증: ... (이유)
문서·계약·ADR 수정: ...
남은 문제·오픈 결정: OPEN-...
```

## 하지 말아야 할 완료 보고

- “Agent Server가 자동 복구를 지원하니까 장애 테스트 완료” (실행 검증이 아님).
- “프롬프트에 써놨으니까 지원 가능 판정 정확함” (Rule Engine 테스트가 아님).
- “초안 다운로드가 됐으니까 신청 완료” (공식 기관 제출과 다름).
