# 단계별 구현·팀 협업 가이드 (제안)

> 책임: 현실적 일정과 대규모 **목표 설계** 사이에 구현 순서를 설명한다. 제품의 최종 범위를 축소한다고 선언하지 않는다.

## 기준

- 교수님의 대규모 사용자 가정이 설계 복잡도의 중요한 배경. 그러나 실제 동시 사용 규모·RPS는 미정이므로 임의 수치 약속 금지.
- 학생이 겪는 핵심 위험은 지원 조건을 잘못 이해하는 것이다. **일단 하나의 장학금이 근거 있게 판정되는지** 증명한 뒤 범위를 넓힌다.
- 한 팀이 FE/BE/수집/검토를 병렬 작업하려면 API 계약과 fixture를 먼저 합의한다.

## 추천 순서

| 슬라이스 | 사용자가 실제로 확인할 변화 | 필수 BR/AC | 인프라 범위 | 넘기기 전에 증명할 것 |
|---|---|---|---|---|
| S0 업무 모델 | 가상 공고 2건, 학생 사실, 검증 근거 정의 | BR-A05/B01/B06 | 파일 fixture·단위 Rule Engine | 테스트 진리표, 원문 버전 근거 |
| S1 자격 확인 | 학생 입력→3값 결과→조건 근거 화면 | BR-B01~B09/AC-B01~B07 | FastAPI/FE 최소 연결 | 모름·불가·가능·빈 규칙 방지 |
| S2 신청 준비 최소 | 준비 시작 최신 확인·체크리스트·직접 제출 안내 | BR-C01/C05/C07/AC-C01,C05,C07 | mock/latest check 허용하되 표시 | 준비!=제출, 최신 확인 실패 UI |
| S3 질문/초안 | 상태 저장·재개·사실 초안·다운로드 | BR-C03/C04/C06/AC-C03/C04/C06 | LangGraph 로컬/기존 Worker | 같은 case 재개/환각 금지 |
| S4 공식 공고 자동화 | 공고 수집·변경감지·원문 검증·검토 | BR-A01~A09/AC-A01~A04, D04 | Crawler/S3/RDS/Outbox | 변경/실패/검토 시 안전 동작 |
| S5 운영·알림·확장 | 신규·변경 가능 학생 안내, 복구/성능 | BR-N01/N02, AC-R*/N01 | 목표 v7 PoC·FCM | 복구·권한·대규모 수치 검증 |

**S0~S5는 개발 순서의 추천이며 완성/착수 상태 아님.** 중간 발표가 C 전체 데모를 요구한다면 S1~S3를 더 작게 세로로 잘라 같은 목표를 증명한다.

## 팀 병렬 작업을 위한 연결점

- 데이터/수집 담당: 원문 구조/공고 버전/검증 상태 계약. **가짜 공고를 검증 완료로 label 하는 fixture는 반드시 `TEST_ONLY`**.
- 판정/신청 준비 담당: AST evaluator, 상태 전이, 필요 질문, 초안 사실성 검증.
- 프론트 담당: 입력·판정 설명·근거·모름·기다림·직접 제출 경계. 도메인 로직 구현 금지.
- 검토/운영 담당: 원문 대비 추출값과 결정 기록. 기관 정책 해석 금지.

각 역할이 맡는 실제 사람은 팀이 재확인해 지정. 역할=별도 저장소/서버 1개가 아니다.

## 배포 경로

로컬 mock 환경 → 진짜 공식 출처 한정 검증 → DB/S3 참조 정합성 → Agent Server 라이선스+PoC → 복구시험 → 교수님 합의 부하 측정 → 목표 클라우드 확대. 무리하게 완성 목록을 먼저 늘리지 않는다.
