# 근거 원장 — 무엇을 사실이라고 말할 수 있는가

> 책임: 원본에서 확인한 사실, 원본 설명의 주장, 팀 설계 가정, 미확인 사실을 구별한다. 기능 정의는 PRD, 업무 규칙은 BR, 아키텍처 결정은 ADR로 이동한다.

## 근거 유형

- `SOURCE-DEFINED` 원본/사용자가 **우리 팀의 정의로 명시**한 내용. 예: 3값 판정, 서류 업로드 제외. 구현 완료 증거는 아님.
- `SOURCE-CLAIM` 기존 설계 파일이 **기능 구현 또는 성능**을 주장한 부분. 현재 저장소를 보지 않아 독립 확인하지 않음.
- `RESEARCH-SUMMARY` 조사 메모/온라인 자료/인터뷰를 합쳐 기술한 문제. 모집단·빈도·발언 원문 검증 불가.
- `PROPOSED` 제공된 자료를 바탕으로 새로 제안한 구체적인 계약/우선순위/필드/예외 처리. 팀 승인 전 확정 아님.
- `OPEN` 확실한 근거가 부족하거나 팀 선택이 필요한 항목.

## 자료 해석의 주의 사항

- `Scholarship AI System Architecture v7.dc(1).html`: **미래 AWS 배포 설계** + 원문이 주장하는 기존 로컬 구현 범위 + 검증 조건. 함께 섞지 않는다. 이 패키지의 `reference/architecture-v7.html`에 원본 보존.
- `06.PRD 작성 & 기술 결정(ADR)`: 단일 기준 문서·Out of Scope·ADR 4요소 작성 방법론. **장학금 사업 도메인 원천**은 아니다.
- `ADR(1).pdf`: 문제/맥락, 대안, 선택, 부정적 결과, 검증을 기록하는 형식의 참고.
- `바이브코딩 팀으로 하면 왜 망할까`: 공유 계약·DoD·작업 단위·하네스의 방법론 참고.
- 3개 도메인 스토리 해설 TXT + 1개 프로젝트 분석 초안: 행위자·현재/미래 구분/스토리맵 자료. `4조 프로젝트 계획서` 원본 PPT 및 v6 원본은 **이번 현재 업로드에 없으며** 사용자가 이번 메시지에 재진술한 A/B/C·D1~D4가 우선 근거다.
- 제공된 조사 메모의 대표 문장은 **합성 예문**이지 특정 인터뷰 응답자 직접 발언이 아니다.

## 인용 원칙

업무 근거를 쓸 때 `EV-xx` 또는 원본 파일명을 함께 기재한다. 외부 기관의 실제 자격 규칙을 인용할 때에는 링크·공고 연도·원문 위치·검증 시각을 새로 남긴다. 답변이 없으면 `확인되지 않음`.
