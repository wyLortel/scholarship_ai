# 변경 관리 — 한 사실의 주인 문서를 먼저 바꾼다

> 책임: 새로운 발견·요구 변경이 생겼을 때 **문서와 코드가 어긋나지 않는 운영 방식**.

## 변경 분류표

| 바뀐 것 | 먼저 수정하는 유일 원본 | 같이 확인할 곳 | 이유 |
|---|---|---|---|
| 실제 인터뷰 발언/공식 원문 추가 | `01-evidence.md` | AS-IS, PRD 문제 설명 | 가정과 실제 사실 구분 |
| 공고의 실제 해석·자격 규칙 | 공식 원문 이력 + `business-rules.md`/`eligibility-policy.md` | AC·fixture·API 결과 | 추측 기반 판정 방지 |
| 제품 범위/우선순위 | PRD | 스토리맵·릴리스·Out of Scope | 팀 승인 유지 |
| 도메인 상태 의미 | `06-state-machines.md` | DTO·DB·테스트·UI | '준비=제출' 같은 혼동 방지 |
| 기술 구성/의존성·서버 실행 | 새 ADR | architecture·CI·운영·계약 | 왜 바뀌었는지 보존 |
| API 요청/응답 필드 | 실제 API 계약(`contracts/` 승인 후) | FE·BE·Agent·fixtures | 병렬 개발 충돌 방지 |
| 테스트 통과 여부 | CI 로그/실행 증빙 | DoD·PR | 체크리스트만으로 완료 주장 금지 |

## PR에 남길 최소 기록

```text
왜 바꿨는가(사용자/운영 사건):
기존 규칙/근거 ID:
새로운 관찰/증거:
대안과 손해:
수정한 단일 원본 문서:
연쇄 영향(상태/API/데이터/테스트/보안):
검증 수행 결과:
실행 못한 위험:
```

## ADR 보존

이미 승인된 결정의 Context와 Consequences를 편집해 과거의 이유를 덮어쓰지 않는다. 새로운 ADR에 `Supersedes: ADR-nnnn`, 바뀐 전제·대안·이주 계획을 적는다. 기존 ADR은 `SUPERSEDED`로 표시하며 링크한다.
