# 인터페이스 설계 가이드

API·모듈 호출·이벤트를 바꿀 때는 소비자가 받은 결과를 어떻게 사용할지 먼저 적는다. 계약에는 형식과 함께 결과의 의미, 실패가 났을 때 할 일, 변경 시 기존 소비자가 받는 영향이 드러나야 한다.

> 팀 검토용 가이드. 실제 통신 스키마의 원본은 [contracts](../../../contracts/README.md), AI 그래프 입출력은 [Agent 계약](../04-agent-workflow-contract.md)이다. 아래 경로와 응답은 [OpenAPI 초안](../../../contracts/api-draft.yaml)의 예시다. 현재 배포에서 사용할 수 있는 API는 실제 라우트와 함께 확인한다.

## 계약을 검토할 때 기록할 항목

| 항목 | 이 서비스에서 확인할 내용 |
|---|---|
| 제공자·소비자 | 판정 API를 만드는 백엔드와 이를 표시하는 프론트, 규칙을 요청하는 유스케이스와 제공하는 공고 모듈처럼 양쪽을 명시한다. |
| 입력과 출력 | 필수값·선택값·null·단위·기준일·식별자·버전과 관련 근거를 확인한다. 표시에 필요한 형태로 내보내고 기관 API 응답, ORM 행, LLM SDK 응답은 연동 어댑터에서 변환한다. |
| 사전조건과 사후조건 | 요청을 처리할 권한과 유효한 대상 버전, 성공 뒤 조회할 수 있는 기록을 적는다. 상태의 의미는 [상태 전이](../../01-domain/06-state-machines.md)와 [UX 계약](../../02-product/03-UX-contract.md)에서 확인한다. |
| 오류와 소비자 행동 | 업무 결과, 버전 충돌, 전송 실패를 구분한다. 기계 분기는 안정된 코드·상태를 기준으로 작성하고 사용자 메시지는 표시용으로 쓴다. |
| 시간과 반복 호출 | 접수와 완료 시점, 시간초과 시 재조회·재시도 방법, 요청 키의 적용 범위와 중복 처리 결과를 확인한다. 처리량과 시간 목표는 OPEN-10, OPEN-12에서 확인한다. |

## 예시로 점검하기

| 계약 | 전달하는 내용과 약속 | 소비자가 볼 실패·검증 사례 |
|---|---|---|
| 프론트 → 판정 API `POST /api/assessments` | 공고 버전과 타입을 갖춘 사실을 전달한다. `200`의 `group`, `details`, `noticeVersionId`, `isStale`을 표시·판정 근거에 사용한다. | 미확인은 결과 안에 담길 수 있다. 버전 충돌·검증 미완료의 `409`에서는 확정 판정이 노출되지 않고 충돌 사유가 전달되는지 AC-B05, AC-B07로 확인한다. |
| 프론트 → 준비 API `POST /api/preparations` | 대상 공고·기대 버전 및 `Idempotency-Key`를 보낸다. `202`의 `caseId`로 진행을 조회한다. | 응답 유실 시 같은 논리적 요청에는 같은 키를 사용하고, 조회 가능한 업무 상태를 확인한다. 준비 완료 표시는 `preparationStatus`에 연결한다. AC-C03, AC-C07, AC-R01과 [ADR-0005](../adr/0005-async-outbox-idempotency.md)를 확인한다. |
| 유스케이스 → 공식 출처 연동 어댑터 | 유스케이스는 원문·첨부 참조와 확인 결과처럼 자신이 필요한 값을 요청하고, 어댑터는 기관별 형식과 네트워크 결과를 변환한다. | 기관 타임아웃과 정상 확인의 구분을 AC-A02, AC-C01로 점검한다. 메서드 이름과 타입은 구현 티켓에서 기존 계약을 확인해 정한다. |

업무 유스케이스가 필요로 하는 연동 계약을 기준으로 어댑터를 연결한다. 기관 연동을 바꿀 때 같은 의미를 제공할 수 있으면 변환과 fixture를 수정한다. 의미까지 달라지면 계약 소비자와 합의한다.

## 호환성 확인

- 필드 삭제·이름 변경·필수 입력 추가·기존 값의 의미 변경은 기존 소비자의 사용 예와 비교한다. 예를 들어 `lastCheckedAt`에 확인 실패 시각을 넣으면 값의 타입이 같아도 의미가 달라진다. 새 enum 값과 추가 응답 필드도 엄격한 소비자에서 처리되는지 시험한다.
- 이용자가 보는 목록의 순서, 오류 코드, 타임아웃 시 행동 중 제공자가 보장하는 것을 문서에 적는다. 프론트 테스트는 사람이 읽는 문구가 바뀌어도 상태·코드 분기가 유지되는지 확인한다.
- 호환성을 깨는 변경이 필요하면 새 형식을 같이 제공하고, 프론트·Agent·mock 등 실제 소비자를 옮긴 다음 구형 형식을 제거한다. 함께 제공하기 어렵다면 버전 분리를 검토한다. 각 단계의 적용 확인과 롤백 조건을 기록한다.

### PR 체크리스트

- [ ] 계약 원본에서 입력, 출력, 상태 의미, 오류 시 호출자 행동과 권한을 확인했다.
- [ ] 이전 소비자와 새 소비자가 받는 값의 단위·버전·상태를 실제 응답 또는 가상 fixture로 비교했다.
- [ ] 변경 영향에 따라 버전 충돌, 알 수 없는 상태, 중복 요청 또는 거부된 접근을 확인했다. 기존 소비자의 전환 순서를 기록했다.
