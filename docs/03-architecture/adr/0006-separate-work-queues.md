# ADR-0006 — Crawler는 직접 Redis Stream, AI/알림은 Agent Server 내장 실행 큐

- 상태: `TARGET-DESIGN` · 최초 기록: 2026-11-18 (제공된 v7/업무 정의를 반영한 **팀 검토용 재구성**)
- 결정 주체: 프로젝트 팀(승인자/승인일 미입력). 이 문서는 라이선스/성능·실배포 검증 증거가 아님.
- 연결 요구사항/근거: `EV-12, EV-10, NFR-03`

## 맥락 — 문제가 무엇이고 왜 결정이 필요한가

초기엔 모든 작업을 Redis Stream 하나로 관리하기 쉬워 보이지만 작업의 재시도/대기/소유 주체가 다르다.

## 선택한 방향(팀 v7/업무 설계의 목표)

직접 관리하는 Stream을 `crawler_jobs`로 한정(ACK/XAUTOCLAIM/DLQ). AI run과 알림 발송은 Agent Server 내장 큐와 체크포인트를 사용(전환 PoC 조건부).

## 검토해야 할 대안(비교 목록)

- 모든 작업을 직접 Redis Stream 구현
- 모든 작업을 Agent Server에 통합
- 별도 메시지 브로커 추가

**선택 기준:** 도메인 정확성·학생 경험·작업 유실 위험·현재 팀 인력과 운영 부담·교수님의 대규모 가정. 대안이 정량 비교되었다는 주장은 하지 않는다.

## 얻는 것

직접 구현해야 할 Lease/heartbeat·재시도 로직 감소, 작업 유형별 책임 분리

## 감수할 대가 — 단점도 기록

Redis·Agent Server 두 관리 영역의 운영 복잡도, Redis 손실에 대한 정합성 재검사 필요

## 무엇을 검증해야 이 결정이 유효한가

수집 도중 종료 후 회수, 중복 스케줄 등록, 알림 대량 발송 시 준비 지연, Agent 강제 종료 시험

## 되돌리거나 변경할 조건

Agent Server 전환 실패 시 자체 Worker 대안 유지/별도 ADR 작성

## 구현·검증 상태

`[ ] 팀 승인` `[ ] 코드 대응 확인` `[ ] 실패 시험 통과` — 세 체크 모두 **검증 전**. ADR이 있다는 이유로 이 항목을 체크하지 않는다.
