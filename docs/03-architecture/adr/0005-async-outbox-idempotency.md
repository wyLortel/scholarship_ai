# ADR-0005 — FastAPI 빠른 접수와 DB Outbox를 이용해 장시간 AI 작업 분리

- 상태: `TARGET-DESIGN` · 최초 기록: 2026-11-18 (제공된 v7/업무 정의를 반영한 **팀 검토용 재구성**)
- 결정 주체: 프로젝트 팀(승인자/승인일 미입력). 이 문서는 라이선스/성능·실배포 검증 증거가 아님.
- 연결 요구사항/근거: `EV-10, BR-C03, NFR-03`

## 맥락 — 문제가 무엇이고 왜 결정이 필요한가

신청 준비·공고 분석이 오래 걸리고 중간에 프로세스가 죽으면 DB 작업과 큐 작업 사이의 전달이 유실될 수 있다.

## 선택한 방향(팀 v7/업무 설계의 목표)

API는 준비 건과 outbox를 같은 DB 트랜잭션으로 기록하고 접수 ID 반환. Relay가 Agent Server run을 생성. API/전달/결과의 3단계 멱등성 및 재정합성 검사 계획.

## 검토해야 할 대안(비교 목록)

- HTTP 요청이 AI 실행 완료까지 기다림
- DB 커밋 후 즉시 Agent Server 호출
- Redis Stream만 영속 작업 진실로 사용

**선택 기준:** 도메인 정확성·학생 경험·작업 유실 위험·현재 팀 인력과 운영 부담·교수님의 대규모 가정. 대안이 정량 비교되었다는 주장은 하지 않는다.

## 얻는 것

빠른 응답과 실행 격리, DB 커밋 후 전달 유실 위험 감소, 재시도 가능

## 감수할 대가 — 단점도 기록

Relay/Outbox 테이블·모니터링 복잡도, at-least-once 전달, 중복 run/외부 부작용 위험

## 무엇을 검증해야 이 결정이 유효한가

API commit 직후 종료, run 생성 직후 Relay 종료, 결과 저장 직전 재실행, outbox 전달 뒤 Redis 손실 시험

## 되돌리거나 변경할 조건

작업량·운영 단순성이 더 중요하고 DB-큐 원자성 문제가 다른 방식으로 해결된다면 재검토
