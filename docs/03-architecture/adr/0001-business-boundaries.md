# ADR-0001 — 업무 경계를 A 수집·검증 / B 자격 판정 / C 신청 준비로 유지

- 상태: `TARGET-DESIGN` · 최초 기록: 2026-11-18 (제공된 v7/업무 정의를 반영한 **팀 검토용 재구성**)
- 결정 주체: 프로젝트 팀(승인자/승인일 미입력). 이 문서는 라이선스/성능·실배포 검증 증거가 아님.
- 연결 요구사항/근거: `EV-02, BR-B02, FR-A01~FR-C05`

## 맥락 — 문제가 무엇이고 왜 결정이 필요한가

기능이 많고 LLM이 개입하면 공고 의미·판정·신청 진행 책임이 뒤섞인다. 팀의 A/B/C 구분을 코드 구조까지 일관되게 연결해야 한다.

## 선택한 방향(팀 v7/업무 설계의 목표)

업무 기준으로 A(공식 원문·검증), B(학생 사실·규칙 평가), C(질문·초안·준비 건)를 구분한다. 별도의 마이크로서비스 3개를 강제하지 않고 논리 모듈 책임부터 나눈다.

## 검토해야 할 대안(비교 목록)

- 단일 AI 프롬프트에 A~C 모두 위임
- API 엔드포인트별로 규칙을 중복 구현
- A/B/C마다 독립 마이크로서비스

**선택 기준:** 도메인 정확성·학생 경험·작업 유실 위험·현재 팀 인력과 운영 부담·교수님의 대규모 가정. 대안이 정량 비교되었다는 주장은 하지 않는다.

## 얻는 것

각 규칙·데이터의 소유권이 분명하고 변경 영향이 한 영역에 국한됨; 개별 도메인 테스트 작성 가능

## 감수할 대가 — 단점도 기록

모듈 경계 설계 비용과 영역 간 DTO/흐름 조정 필요; 초기 작은 코드에서는 분리가 다소 번거로울 수 있음

## 무엇을 검증해야 이 결정이 유효한가

Rule Engine만 판정 값을 생성하는지 코드 의존성 검사; 공고 버전 변경이 C에 어떻게 전파되는지 통합 시험

## 되돌리거나 변경할 조건

업무 영역이 실제로 겹치거나 책임 중복이 생기면 도메인 스토리에서 시작하여 경계 재검토

## 구현·검증 상태

`[ ] 팀 승인` `[ ] 코드 대응 확인` `[ ] 실패 시험 통과` — 세 체크 모두 **검증 전**. ADR이 있다는 이유로 이 항목을 체크하지 않는다.
