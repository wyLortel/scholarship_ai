# ADR-0013 — 프론트엔드는 Next.js App Router, 서버 컴포넌트 기본

- 상태: `TARGET-DESIGN` · 최초 기록: 2026-11-18 (MVP 착수 중 팀원 결정 — #22에서 Vite 템플릿을 만든 뒤 전환)
- 결정 주체: 프로젝트 팀(팀원 결정, 팀 전체 승인 체크 미완). 이 문서는 SEO 효과·성능 측정 증거가 아님.
- 부분 대체(Supersedes 일부): [ADR-0008](0008-single-ec2-eight-containers.md)의 웹 서버 구성 `Nginx + React(정적 빌드)` → `Nginx + Next.js 서버`. ADR-0008의 나머지(단일 EC2, 관리형 RDS/S3 등)는 유지.
- 연결 요구사항/근거: `ST-01, FR-B03, FR-B04, NFR-04, BR-B02, BR-A05`

## 맥락 — 문제가 무엇이고 왜 결정이 필요한가

1. **검색 유입(SEO).** 학생 B(PRD §2)는 "제도 이름·검색어를 모름"(P-01)에서 출발한다. 학생이 검색창에 "2027 서울 대학생 장학금"처럼 검색해 우리 공고 상세로 바로 들어오게 하려면, 공고마다 고유 URL이 있고 제목·모집 기간·기관·공식 출처가 **처음 응답 HTML에 들어 있어야** 유리하다. 클라이언트 렌더링만 하는 Vite SPA는 검색엔진이 JavaScript를 실행해야 내용을 보게 된다.
2. **공고별 검색 제목·설명.** 공고마다 `<title>`·description·Open Graph를 다르게 만들어야 한다. Next.js는 라우트별 `generateMetadata`로 이를 서버에서 만든다.
3. **전환 시점.** 공고 페이지가 많아지고 URL이 외부에 퍼진 뒤 바꾸면 URL·메타데이터 이전 비용이 커진다. 화면이 health 하나뿐인 지금(#22)이 비용이 가장 적다.

## 선택한 방향

- **Next.js App Router + TypeScript.** `frontend/`에 둔다. 판정·규칙은 계속 FastAPI(Rule Engine, ADR-0002)가 소유한다.
- **구현 방식: 서버 컴포넌트가 기본**(전환 이유가 아니라 App Router의 사용 방식). 데이터를 읽어 보여주는 화면(공고 목록·상세·근거·판정 결과 표시)은 서버 컴포넌트가 FastAPI를 직접 호출해 렌더링한다. **클라이언트 컴포넌트는 상호작용이 필요한 부분만** 쓴다(입력 폼, 펼치기, 체크박스).
- **API 경로:** 서버 컴포넌트 → `API_ORIGIN`(서버 전용 환경변수, compose에서 `http://backend:8000`)으로 직접 호출. 브라우저의 `/api/*` 요청은 Next `rewrites`로 FastAPI에 전달.
- **공개 페이지와 개인 페이지 구분:**
  - 공개(검색 노출 대상): **검증된(VERIFIED) 공고** 목록·상세만. 공고별 메타데이터 생성. 정적 생성/재검증 캐시 허용.
  - 개인(검색 비노출): 학생 입력·판정 결과·준비 건·초안. `noindex`, 요청마다 렌더링(`cache: 'no-store'`/dynamic), **사용자 간 캐시 공유 금지**.

## 서버 컴포넌트에서도 지킬 규칙

- **서버 컴포넌트도 자격을 계산하지 않는다.** 서버에서 돈다고 Rule Engine이 아니다. 판정은 FastAPI 응답을 표시만 한다(UX 계약, BR-B02). `NEEDS_REVIEW`를 `ELIGIBLE`로 바꾸지 않는다.
- **미검증 공고는 공개 페이지·sitemap·메타데이터에 넣지 않는다**(BR-A05). `TEST_ONLY` 가상 공고는 `noindex`로 검색 노출을 막는다.
- **개인 데이터는 캐시하지 않는다.** 판정·초안·프로필을 정적 생성하거나 Next 데이터 캐시에 저장하면 다른 학생에게 보일 수 있다(NFR-04). 개인 데이터 fetch에는 반드시 no-store.
- **비밀값은 서버 전용.** `NEXT_PUBLIC_` 접두어 변수에 토큰·내부 주소를 넣지 않는다(CLAUDE.md §2-9). 서버 전용 모듈은 클라이언트 번들에 들어가지 않게 분리한다.
- 공고 상세 HTML에 들어가는 원문 근거는 **검증된 버전·확인 시각**과 함께 둔다(BR-B06). 오래된 정적 페이지가 "최신"으로 보이지 않게 재검증 주기·마지막 확인 시각을 화면에 표시한다(BR-A09).

## 검토한 대안

| 대안 | 얻는 것 | 잃는 것 |
|---|---|---|
| Vite + React SPA 유지 (#22에서 먼저 만든 구성) | 단순, 정적 파일만 서빙, 이미 동작 | 공고 상세 SEO·공고별 메타데이터 불리 |
| Vite SPA + 사전 렌더링(prerender) 플러그인 | SPA 구조 유지하며 일부 HTML 생성 | 공고가 수시로 바뀌는 데이터라 빌드 시점 렌더링과 안 맞음, 공고별 메타데이터 관리 별도 |
| Remix/React Router 프레임워크 모드 | 서버 렌더링 가능 | 팀 경험·자료가 Next보다 적음 |
| **Next.js App Router (선택)** | 라우트별 메타데이터·초기 HTML·정적/동적 렌더링 선택 | Node 서버 실행 필요, 캐시 규칙 실수 시 개인정보 노출 위험, 학습 비용 |

**선택 기준:** 검색 유입 가능성(학생 B), 개인 데이터 캐시 위험을 규칙으로 통제 가능한지, 전환 비용(지금 vs 공고 페이지가 늘어난 뒤), 내일 데모 일정 영향. 정량 비교(SEO 유입량 등)는 하지 않았다.

## 얻는 것

공고별 고유 URL·메타데이터·초기 HTML, 화면별로 정적/동적 렌더링 선택.

## 감수할 대가 — 단점도 기록

- 웹 계층에 **Node 서버 프로세스**가 생긴다(정적 파일만 서빙하던 Nginx 대비 메모리·장애 지점 증가). ADR-0008의 컨테이너 수·자원 측정에 반영해야 한다.
- Next 캐시 기본 동작을 잘못 쓰면 개인 판정이 다른 사용자에게 캐시되어 보일 수 있다 → 위 규칙과 코드 리뷰로 통제.
- 데모 하루 전 전환으로 #22를 다시 작업(Vite 템플릿 제거). 학습 비용.

## 무엇을 검증해야 이 결정이 유효한가

- 공고 상세의 첫 응답 HTML에 제목·기관·모집 기간·공식 출처가 들어 있는지(`curl`로 확인).
- 학생 A·B가 같은 판정 화면 URL을 열어도 서로의 결과가 보이지 않는지(캐시 시험, AC-R05와 함께).
- 미검증·`TEST_ONLY` 공고가 sitemap·메타데이터에 없는지.
- 단일 EC2에서 Next 서버 포함 자원 사용량(ADR-0008 측정 항목).

## 되돌리거나 변경할 조건

검색 유입을 목표로 하지 않기로 하거나(학생 유입이 학교 공유 링크 중심), Node 서버 운영 부담이 측정상 감당 불가하면 정적 SPA로 되돌린다. 화면 계층만 바뀌므로 FastAPI·Rule Engine은 영향 없음.

## 미확정

- Nginx와 Next 서버를 한 컨테이너로 둘지 분리할지 — 배포 이슈에서 결정.
- 공개 공고 페이지의 재검증 주기 — 공고 최신성 확인 방식(OPEN-06)과 같이 결정.
- 실제 공고 공개 자체는 공식 출처·수집 허용 정책(OPEN-01) 확정 후.
