# ADR-0003 — 공고 버전 보존과 원문 근거 검증 후 색인

- 상태: `TARGET-DESIGN` · 최초 기록: 2026-11-18 (제공된 v7/업무 정의를 반영한 **팀 검토용 재구성**)
- 결정 주체: 프로젝트 팀(승인자/승인일 미입력). 이 문서는 라이선스/성능·실배포 검증 증거가 아님.
- 연결 요구사항/근거: `EV-03, BR-A01, BR-A02, BR-A03, BR-A04, BR-A05, BR-A06, BR-A07, BR-A08, BR-A09, FR-A01, FR-A02, FR-A03, FR-A04`

## 맥락 — 문제가 무엇이고 왜 결정이 필요한가

공고를 다시 수집했거나 LLM이 조건을 추출한 것만으로 최신·정확성을 보장할 수 없다. 공고 변경 시 학생이 과거 판정으로 준비할 위험이 있다.

## 선택한 방향(팀 v7/업무 설계의 목표)

NoticeVersion을 불변 이력으로 보존하고 근거 anchor를 함께 관리. 검증된 rule set만 판정/공개 색인 대상으로 사용. 변경 시 새 버전 재검증·기존 판정 재평가.

## 검토해야 할 대안(비교 목록)

- 최신 공고 행을 덮어쓰기
- LLM 결과 즉시 공개
- 벡터 유사도 점수만 근거로 표시

**선택 기준:** 도메인 정확성·학생 경험·작업 유실 위험·현재 팀 인력과 운영 부담·교수님의 대규모 가정. 대안이 정량 비교되었다는 주장은 하지 않는다.

## 얻는 것

판정 재현·감사·오정보 노출 감소·과거 판정 추적

## 감수할 대가 — 단점도 기록

버전/첨부 스토리지·검토 비용 증가, 조건 검증 지연, 오래된 판정 무효화 로직 필요

## 무엇을 검증해야 이 결정이 유효한가

신규/변경/동일/접속실패 시험; 잘못된 추출 검토; 원문 수정 후 stale 재평가; 미검증 인덱스 비노출

## 되돌리거나 변경할 조건

원문 관리 비용이 심하면 보존 기간 정책을 합의하되 삭제로 감사성을 깨지 않도록 설계

## 구현·검증 상태

`[ ] 팀 승인` `[ ] 코드 대응 확인` `[ ] 실패 시험 통과` — 세 체크 모두 **검증 전**. ADR이 있다는 이유로 이 항목을 체크하지 않는다.
