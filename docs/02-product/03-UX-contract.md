## 화면과 정보

| 화면 | 사용자 행동 | 반드시 표현할 데이터 | 위험한 문구·동작 |
|---|---|---|---|
| 홈 | 서비스 이해·공고 둘러보기 | 가상/실제 공고 구분 배지, 공식 출처 표시. 판정 배지는 **그 공고의 판정 응답이 있을 때만** 표시(로그인 여부와 무관), 응답이 없으면 "내 정보로 확인하기" 안내 | 판정 응답이 없는 공고에 `가능`·`불가` 배지 표시 |
| AI 상담(채팅) | 말로 묻고 부족한 사실 보완 | 지금 쓰는 내 정보, 왜 묻는지와 관련 원문 조건, `모름` 선택, 판정 카드(API 결과 그대로)·조건별 결과·원문 근거·공고 버전, 준비 ≠ 제출 안내 | AI 문장이 API와 다른 판정을 말함, 모름을 `충족`으로 표시, 대화 속 소득·성적을 로그에 남김 |
| 장학금 목록 | 후보 발견/필터 | 제목, 기관, 공식 출처 링크, 모집 기간, 확인일, 가능/확인 필요/불가 그룹(공고별 판정 응답 기준, 그룹별 개수는 응답을 세기만) | `확인 필요` 숨긴 채 추천 목록에서 제거 |
| 프로필 입력 | 학적/지역/소득 입력 | 필요한 사실·단위·기준 연도·`모름` 선택 | 모름을 `0`, `미해당`으로 저장 |
| 공고 상세 | 자격 이해 | 조건별 PASS/FAIL/UNKNOWN, 이유, 공식 원문 문장·위치, 공고 버전, 확인 시각 | 출처 없이 'AI가 가능이라 판단' |
| 준비 시작 | 최신 상태 확인 | 새로 확인한 시각, 이전 판정, 변경/확인 실패 여부, 위험 안내 | 네트워크 실패를 ‘최신’으로 표시 |
| 추가 질문 | 부족한 사실 보완 | 왜 묻는지, 어떤 원문 조건 때문인지, `지금 모름` 선택, 이어하기 | 답변 안 했는데 PASS 표시 |
| 서류 체크리스트 | 발급 준비 | 이름, 조건부 요구 여부, 공식 발급/확인 경로, 사용자 확인 체크, 원문 근거 | 우리 서비스에 개인 증빙 업로드 요청 |
| 작성 초안 | 학생 사실 검토 | 공고 문항, 초안/플레이스홀더, 사용 사실, 미확인 주장, 다운로드 | 공식 제출 성공 문구 |
| 관리자 검토 | 근거 정합성 검토 | 원문 버전·문장, 추출 후보, 실패 사유, 승인/수정/반려 이유 | 학생 선발 승인 버튼 |
| 알림함 | 공고 신규/변경 확인 | 공식 공고·발송 기준 버전·알림일·현재 상태 | 푸시 발송 성공을 기기 읽음으로 표시 |

## 사용자의 의사결정 순간별 카피

- **가능:** “입력한 정보와 확인된 공고 조건에서는 지원 요건을 충족합니다. 실제 선정은 해당 기관이 판단합니다.”
- **불가:** “이 공고의 [조건명]이 입력 정보와 맞지 않습니다. [공식 원문 근거]를 확인해 주세요.”
- **확인 필요(학생 답변):** “소득구간을 입력하지 않아 판단을 마치지 못했습니다. 공고 기준연도 값을 확인해 주세요.”
- **확인 필요(기관):** “이 조건은 공식 기관의 해석이 필요합니다. 저희가 임의로 결정하지 않습니다.”
- **공고 변경:** “이전 판정은 과거 버전을 기준으로 합니다. 변경된 공고를 다시 확인해 주세요.”
- **재확인 실패:** “현재 공식 공고의 최신 상태를 확인하지 못했습니다. 마지막 확인: [시각].”
- **준비 완료:** “신청에 필요한 자료를 정리했습니다. 제출과 증빙 발급은 공식 기관에서 직접 진행해 주세요.”
- **확인 사항 남음:** “자료는 준비되었지만 [미확인 항목]은 공식 제출 전 확인이 필요합니다.”

## 접근성/모바일 UX (제안)

- 색상 하나로 상태 전달하지 않고 텍스트·아이콘·이유를 같이 보여준다.
- 누락값을 되돌릴 수 있고, 질문을 미루거나 보존할 수 있어야 한다.
- 근거 원문 링크는 새 창에서 열더라도 공고 버전·문서 제목을 표시한다.
- 긴 설명은 처음에 결론+조건별 핵심, 클릭 시 원문 펼치기. 단, 근거가 감춰져 사라지는 UI 금지.
- 개인정보를 공유하기 전에 어떤 사실을 왜 묻는지 보여준다.

## UX에서 계산해서는 안 되는 것

React 컴포넌트 내부에서 `grade>=2 && income<=5`처럼 자격을 독자 계산하지 않는다. 받은 Rule Engine 결과와 증거를 표현하는 데 집중하고, API가 `NEEDS_REVIEW`이면 프론트가 임의로 `ELIGIBLE`로 올리지 않는다.

**AI 상담도 같다.** 채팅 응답 문장(정해진 문구든 LLM이든)은 판정을 만들거나 바꾸지 않는다. 대화에서 받은 사실은 Rule Engine API로 보내고, 돌아온 결과를 카드로 표시한 뒤 그 결과를 설명만 한다(AC-B06). 결과가 오기 전에는 "확인 중"으로 두고 `가능`·`불가`를 먼저 말하지 않는다.
