# PRD — 장학금 통합 지원 AI

> 버전 `0.2` / **팀 승인 전** / 2026-11-18. 책임: 제품 **목표, 사용자 가치, 범위, 기능 요구, 성공 조건**을 명시한다. 비즈니스 계산은 `../01-domain/`, 기술 선정의 대안·트레이드오프는 `../03-architecture/adr/`에만 둔다.

## 1. 제품을 왜 만드는가

**문제:** 대학생은 장학금을 찾는 방법을 모르거나, 다른 지역·과거 공고가 섞여 있고, 소득·학적 등 공식 조건을 자신에게 적용하기 어렵다. 현재 조사 내용은 인터뷰+온라인 메모의 요약이며 확정적 통계가 아니다(`EV-13`).

**비전:** 학생이 **공식 공고를 찾고, 자신의 조건으로 검증 가능한 근거와 미확인 항목을 구분하며, 실제 제출 전에 필요한 서류와 초안을 준비**하도록 돕는다.

**JTBD:** “장학금 신청을 고민할 때, 지원 자격과 최신 공고를 반복해서 읽어야 하는 부담을 줄여, 잘못된 확신 없이 다음 행동을 결정하고 싶다.”

**왜 챗봇이 핵심이 아닌가?** 학생의 목적은 챗봇과 대화하는 것이 아니라 `공식 근거·판정·준비 자료`를 얻는 것이다. 챗봇/에이전트는 필요할 때만 쓰는 수단.

## 2. 사용자와 업무 경계

| 주 사용자 | 목표 | 시작 계기 | 제품에서 끝나는 순간 |
|---|---|---|---|
| 학생 A: 공고를 이미 찾음 | 조건 충족 여부 확인·준비 | 공고가 어렵거나 모르는 정보 있음 | 근거·질문·체크리스트/초안을 보고 준비 상태 이해 |
| 학생 B: 공고를 못 찾음 | 공식 공고 발견 | 제도 이름·검색어 모름 | 후보와 공식 출처/모집 기간 확인 후 A의 흐름 진입 |
| 내부 검토자 | 원문과 AI 추출값의 정합성 확인 | 불일치·모호한 추출 | 승인/수정/반려와 이유를 기록하고 재개/중단 |

이름이 붙은 페르소나는 합성(실제 응답자 동일시 금지). **서비스 바깥:** 증빙서류 발급·검증, 공식 기관 제출, 심사, 선발, 지급.

## 3. 제품의 핵심 결과와 성공 모습

1. 학생이 결과가 **가능/불가/확인 필요 중 무엇인지**와 **왜** 그런지 설명할 수 있다.
2. 모든 자격 판단에는 **공식 근거, 공고 버전, 마지막 확인 시점, 학생이 제공한 정보**를 추적할 수 있다.
3. 모르는 정보와 원문 자체의 모호함을 구분해 **학생 질문/기관 확인/관리자 검토**로 적절히 넘긴다.
4. 공고가 바뀌면 옛 판정·초안을 최신으로 위장하지 않는다.
5. 학생이 공고별 준비 항목과 확인된 사실에 근거한 초안을 확인·다운로드할 수 있다.
6. 신규·변경 공고를 검증한 다음 `가능`인 학생에 대해 알림을 준비할 수 있다(알림 정책 및 출시 단계 별도 승인).

**R1/R2/R3는 이 문서 작성자가 제안한 구현 순서**이고 실제 완료 상태가 아니다. 지도교수의 시연 요구나 팀 여건에 따라 승인이 필요하다. 기능이 R3여도 **원래 목표 범위에서는 빠진 것이 아니다**.

## 5. 이번 제품의 범위에서 제외할 것 (Out of Scope)

- 학생 대신 외부 공식 기관 사이트에 **자동 제출**하거나 접수 성공으로 표시하는 일.
- 장학금 기관이 하는 심사·선발·지급, 선발 확률 예측, 자격의 공식 인증.
- 학생의 개인정보 증빙서류 파일 **업로드·보관·진위 검증**(v6에서 범위 변경).
- 학적/대학 행정정보 시스템 연동 및 모든 기관 정보의 무제한 수집.
- 공식 출처로 확인되지 않은 뉴스·블로그 정보를 판정 원문으로 사용.
- 대규모 다중 AZ 무중단/고가용성 배포를 초기 EC2 1대 그림에서 이미 완성했다고 주장.

## 8. 전략적 범위의 균형

제품은 A·B·C 전체를 목표로 하지만 **수업 시연**과 **실운영 완성**은 별개. 먼저 `검증된 소수 공고 → 조건별 판정+근거 → 최소 준비 결과`를 끝까지 연결하고, 다음에 자동 수집·중단/재개·초안·검토·알림을 단계적으로 붙이는 **제안**. 이 이유는 가장 큰 위험(틀린 적격 판단)을 초기에 검증하기 위함이지, 교수님의 대규모 요구를 무시하려는 것이 아님.

## 9. 분석 지표(측정 계획, 성과 주장 아님)

- 오류율: 확정 FAIL 조건을 가진 학생에게 `가능`이라고 보여준 사례 수.
- 근거 연결률: 사용자에게 제시한 조건별 판단 중 검증된 원문 위치/버전이 연결된 비율.
- 이해도: 테스트 사용자가 3값 판정과 다음 행동을 설명할 수 있는지.
- 최신성: 바뀐 공고에 대해 이전 판정이 최신으로 노출되는 사례 수.
- 사용성: 학생이 서류 준비를 완료하는 데 걸린 시간(사전/사후 실제 측정 전 수치 없음).
- 운영: 재처리 중복, 검토 대기 적체, 학생 질문 대기 재개 실패율.

## 10. 의존성과 승인

- 공식 출처 데이터/수집 허용 정책, 학적·소득 해석, 교수님 부하 목표, AI API 비용, 관리자 운영, Agent Server 라이선스·PoC가 선행 의존성이다. `../00-governance/03-open-decisions.md`에 추적.
- 이 PRD는 **제품 의도에 대한 실행 가능한 초안**이다. 수용 기준은 테스트로 검증, 정책은 팀이 승인, 구현 완료는 코드·데모로 확인한다.

### 대표적인 사용자 시연 흐름

1. R1(핵심 업무 검증): **가상 검증 공고 2건**에서 학년/소득 `모름` 입력 → 3값 결과와 원문 근거 → 체크리스트(가능하면 최소 한 개).
2. R2(업무 유지·확장): 학생 대기/재개, 변경된 공고 재판정, 내부 검토, 사실 기반 초안 다운로드.
3. R3(운영 자동화): 기관 수집 API·Playwright 확장, 알림함/FCM, 트래픽·복구 검증.

일정·실제 누가 언제 구현하는지는 팀 결정. **원래 목표 업무 A/B/C 전체를 유지하면서** 한 번에 끝까지 작동하는 작은 슬라이스부터 검증하려는 제안이다.

## 12. 구현 순서 — 슬라이스 S0~S5 (제안, 구현 순서의 유일 원본)

> 현실적 일정과 대규모 **목표 설계** 사이에 구현 순서를 설명한다. 제품의 최종 범위를 축소한다고 선언하지 않는다.

### 기준

- 교수님의 대규모 사용자 가정이 설계 복잡도의 중요한 배경. 그러나 실제 동시 사용 규모·RPS는 미정이므로 임의 수치 약속 금지.
- 학생이 겪는 핵심 위험은 지원 조건을 잘못 이해하는 것이다. **일단 하나의 장학금이 근거 있게 판정되는지** 증명한 뒤 범위를 넓힌다.
- 한 팀이 FE/BE/수집/검토를 병렬 작업하려면 API 계약과 fixture를 먼저 합의한다.

**S0~S5는 개발 순서의 추천이며 완성/착수 상태 아님.** 중간 발표가 C 전체 데모를 요구한다면 S1~S3를 더 작게 세로로 잘라 같은 목표를 증명한다.

### 팀 병렬 작업을 위한 연결점

- 데이터/수집 담당: 원문 구조/공고 버전/검증 상태 계약. **가짜 공고를 검증 완료로 label 하는 fixture는 반드시 `TEST_ONLY`**.
- 판정/신청 준비 담당: AST evaluator, 상태 전이, 필요 질문, 초안 사실성 검증.
- 프론트 담당: 입력·판정 설명·근거·모름·기다림·직접 제출 경계. 도메인 로직 구현 금지.
- 검토/운영 담당: 원문 대비 추출값과 결정 기록. 기관 정책 해석 금지.

각 역할이 맡는 실제 사람은 팀이 재확인해 지정. 역할=별도 저장소/서버 1개가 아니다.

### 배포 경로

로컬 mock 환경 → 진짜 공식 출처 한정 검증 → DB/S3 참조 정합성 → Agent Server 라이선스+PoC → 복구시험 → 교수님 합의 부하 측정 → 목표 클라우드 확대. 무리하게 완성 목록을 먼저 늘리지 않는다.
