# domain-ux-rules.md — 장학금 AI UI에서 절대 어기면 안 되는 규칙

> 스크린샷에서 확인한 제품 의도를 토대로 작성한 **화면 표시 규칙(제안)**이다. 규칙의 원본은 [UX 정보 계약](../02-product/03-UX-contract.md), [업무 규칙](../01-domain/04-business-rules.md), [자격 판정 정책](../01-domain/05-eligibility-policy.md)이다. 충돌하면 원본을 따르고 이 문서를 고친다.

## 1. 자격 상태

| 내부 표시 개념 | 사용자 문구 | 조건 | 다음 행동 |
|---|---|---|---|
| possible | **조건상 가능** | 비교 가능한 모든 필수 조건 충족, 미확인 필수조건 없음 | 공식 공고 모집 상태 확인 및 준비 |
| needs-info | **확인 필요** | 필수 조건의 사용자 정보가 없거나 모름 | 무엇을 어디서 확인할지 질문·안내 |
| ineligible | **현재 정보 기준 불가** | 검증 가능한 필수 조건 미충족 | 불충족한 조항/사실 제시 |
| pending-source-review | **판정 보류** | 공식 근거 검증 실패·추출 불일치 | 운영자 검토 또는 공식 원문 확인 |
| stale-result | **재판정 필요** | 공고 버전 변경, 프로필 사실 기준 변경 | 최신 버전과 최신 정보로 다시 비교 |

### API 응답과의 대응 (화면은 이 값만 보고 상태를 고른다)

| 화면 상태 | API 값 (`AssessmentResult`, #23 계약) |
|---|---|
| possible — 조건상 가능 | `eligibilityResult = ELIGIBLE` |
| needs-info — 확인 필요 | `NEEDS_REVIEW` + 조건 `reasonCode = MISSING_FACT` 또는 `INSTITUTION_CONFIRMATION` |
| ineligible — 현재 정보 기준 불가 | `INELIGIBLE` |
| pending — 판정 보류 | `NEEDS_REVIEW` + `RULE_UNVERIFIED`·`UNSUPPORTED_OPERATOR`, 또는 `409 NOTICE_NOT_VERIFIED` |
| changed — 재판정 필요 | `isStale = true` |

**우선순위 제안**: 검증 가능한 필수 조건이 명백히 미충족되면 `ineligible`을 설명하되, 출처 자체가 검증되지 않은 경우에는 함부로 불가/가능으로 확정하지 않는다. 조건 조합(AND/OR), 예외, 제외 조항 및 복수 요건은 서버 도메인 로직이 판단한다. UI가 임의 계산하지 않는다.

## 2. 모집 상태 ≠ 자격 상태
- `모집 상태 미확인`, `모집 중(공식 확인)`, `모집 종료`는 자격과 독립된 축.
- 어떤 공고에 조건상 가능하더라도 모집 종료/미확인 상태면 '지금 신청 가능'이라고 안내하지 않는다.
- '조건상 가능'을 '선정 가능성이 높다', '합격', '최종 자격 확정'으로 번역하지 않는다.

## 3. 근거/버전
- 최소 정보: 기관명, 공고 ID, 공고 버전, 추출된 조항, 사용된 학생 사실, 판단 시점.
- 공식 원문 URL/페이지/문단 식별자는 **있는 경우에만** 표시하고 없으면 '공식 URL 미등록'으로 처리.
- 가상 시연 데이터라면 모든 카드·근거·관리자 검토 화면에서 '시연용/가상'을 눈에 띄게 표시.
- 공고가 바뀌면 이전 판정은 그대로 현재 판정으로 재사용하지 않는다. 차이와 재판정 필요를 분리해 보여준다.

## 4. 회원정보/대화의 사실 출처
- profile: 프로필 저장값(아직 증빙으로 검증된 것은 아닐 수 있음)
- student-confirmed: 채팅에서 학생이 직접 답한 값(자기진술)
- source-extracted: 원문에서 AI가 추출한 조건(검증 대기 가능)
- unverified: 모름/추론 불가/자료 없음
- **로그인 성공만으로 학적·소득이 검증된 것으로 표현하지 않음**.
- 생년월일, 소득구간, 활동 경험은 필요성을 설명하고 최소 수집. 민감한 정보를 공개 UI에 광범위하게 반복 표시하지 않음.

## 5. AI의 질문 전략
1. 이미 저장된 사실과 대상 공고의 필요 조건 비교.
2. 오직 판단/준비에 꼭 필요한 누락 정보를 선택.
3. 질문마다 왜 필요한지 알려줌.
4. 대답 선택지에는 적절할 때 `모름`, `확인 방법`, `나중에 답하기`를 제공.
5. 사용자가 답하면 '학생 답변'으로 출처 표기 후 재비교(저장 동의/정책 준수).
6. 유사한 공고라도 요구 조건이 다르면 화면을 새로 만들지 않고 `MissingInfoQuestion`을 조합함.

## 6. 초안 생성 정책
- 초안 출처: 저장 회원정보/공고 요구 문항/채팅에서 학생이 확인해 준 사실.
- 추측/환각 금지: 지원 이유, 경력/봉사 실적, 활동 수치, 증빙 사실을 지어내지 않는다.
- 미확인 문항: `[추가 확인 필요: 본인의 지원 동기]`처럼 **문서 내부 자리표시자**로 남김.
- 사용자에게 편집/저장/내보내기 가능하게, 문서 생성 후 '본인 검토 필수'를 명시.
- 공식 제출/증빙 발급/기관 심사/지급은 범위 밖이며 실행 버튼으로 오인시키지 않는다.

## 7. 관리자가 승인하는 것
- 승인 대상은 **공식 원문의 판독/조건 추출 정합성**.
- 승인 버튼이 **학생 개인의 자격 승인** 또는 장학금 심사 승인으로 해석되지 않게 안내.
- 승인에는 검토 근거, 변경 전후 값, 승인자, 시점 등 감사 기록을 남길 수 있게 설계(백엔드 계약은 별도 정의).

## 8. 접근성 및 보호
- 필드 label과 오류 메시지 연결; `aria-live`로 응답 도착 또는 저장 결과 알림.
- 키보드만으로 추천→상세→채팅→초안 흐름 완주 가능.
- 버튼의 색·아이콘만으로 의미 전달 금지.
- 선택된 장학금과 진행 중인 대화가 달라지면 컨텍스트를 명시적으로 보여주기.
- 저장 여부/공고 변경 여부/시연 여부는 꾸밈이 아니라 사용자 결정에 필요한 정보.
