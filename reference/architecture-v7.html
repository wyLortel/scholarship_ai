학생이 "신청 준비하기"를 누르면
① 웹 서버 → API 서버로 요청
② API 서버가 신청 건(jobs)과 outbox 기록을 한 트랜잭션으로 DB에 저장하고 바로 "접수됨" 응답
③ Outbox Relay가 Agent Server에 run 생성 (HTTP) → Agent Server가 그래프 실행
④ 학생에게 물어볼 게 생기면 interrupt — Checkpoint가 DB에 저장되고 멈춤 → Agent Server 스트리밍 → API 서버 → 학생 화면에 질문 표시
⑤ 답변이 오면 같은 길로 들어가 멈춘 곳부터 다시 실행 (확인 안 된 정보는 UNKNOWN · 기관 확인 필요로 남김)
⑥ 필요 서류 체크리스트 · 발급 방법 안내 + 자기소개서 · 학업계획서 · 신청서 초안 생성 → 학생이 확인 · 다운로드 후 공식 사이트에서 직접 신청
새 장학금 발견 → 학생에게 알림
1. 찾기 — 수집 서버
① 내장 스케줄러가 정해진 시간에 crawler_jobs에 "수집해" 등록
② 수집 서버가 꺼내고, DB에서 출처 목록 · 이전 해시를 읽음
③ 기관 사이트에서 공고 · 첨부파일을 가져와 해시 비교 → 새 공고 · 바뀐 공고만 남김
④ 원문(PDF · HWP)을 S3에 저장하고, 공고 버전과 outbox("분석해 줘 + 파일 위치")를 DB에 기록 → Relay가 분석 run 생성
2. 분석 — Agent Server
⑤ Agent Server가 분석 run을 실행하고 S3 원문을 읽음
⑥ LLM으로 자격 조건 추출 → 원문 근거 검증 (확신 없으면 관리자 검토로 멈춤)
⑦ 통과하면 공고 · 조건 · 임베딩을 DB에 저장
3. 맞는 학생 찾기 — Agent Server
⑧ 가입한 학생 프로필과 비교해 자격 판정 → "가능"인 학생 목록
⑨ 그 학생들의 기기 토큰을 DB에서 모으고, 학생마다 알림 기록 저장 (앱 알림함용)
4. 보내기 — Agent Server → FCM
⑩ 기기 토큰을 500개씩 묶어 묶음마다 알림 발송 run 생성 (1,200대 → run 3개)
⑪ Agent Server 큐가 run을 차례로 실행 → FCM에 "이 토큰들에게 보내줘" 요청
⑫ FCM(구글)이 학생 휴대폰 · 브라우저에 알림을 띄움 → 실패 토큰 재시도 · 만료 토큰 삭제
5. 확인 — API 서버
⑬ 학생이 알림을 눌러 들어오면 API가 DB에서 추천 목록 · 알림함을 보여줌 (알림 권한 없는 학생도 알림함에서 확인)
AI가 확신하지 못하면 → 관리자
① Agent Server가 검토 요청을 DB에 남기고 interrupt로 멈춤
② Agent Server 스트리밍 → API 서버 → 관리자 화면에 알림
③ 관리자가 승인 / 수정 / 반려
④ API 서버가 결정과 outbox를 저장 → Relay가 resume run 생성 (Command(resume)) → 멈춘 곳부터 재개

① Checkpointer — PostgreSQL로 확정
결정 완료
일반 DB 저장(회원 · 공고 · 신청 상태)과 Checkpoint(멈춘 지점부터 다시 실행하기 위한 상태)는 다르다. LangGraph 공식 Checkpointer가 PostgreSQL · SQLite · MongoDB 기반이라 RDS를 MySQL에서 PostgreSQL로 변경했다. 업무 데이터와 Checkpoint 모두 같은 RDS PostgreSQL에 저장. v6에서는 Agent Server가 Checkpoint를 직접 관리 (업무 DB와 database만 분리).
② Redis Stream 분리
매우 높음
Redis 서버는 하나 그대로. 우리가 직접 관리하는 Stream은 crawler_jobs 하나만 남고, AI 실행 · 알림 발송 큐는 Agent Server 내장 큐가 맡는다. 서로 다른 종류의 작업이 한 대기줄에 섞이지 않게 하기 위함.
③ 장애 복구 책임 분리
높음
AI 작업: Agent Server가 실행 중 꺼진 run을 다시 실행하고 Checkpoint에서 이어간다 (직접 구현 X). 수집 작업: Crawler가 crawler_jobs를 가져간 뒤 꺼지면 XAUTOCLAIM으로 다시 가져가고, 반복 실패는 DLQ로. 어느 쪽이든 재실행될 수 있으니 결과 저장은 멱등하게.
④ 검증 후 색인
높음
수집 → 조건 추출 → Evidence 검증 → 판정. 성공하면 RDS에 승인 기록과 embedding(pgvector)을 같은 트랜잭션으로 저장, 실패하면 관리자 검토. 원문을 읽었다고 추출한 조건까지 정확한 것은 아니기 때문.
⑤ Crawler와 MCP 역할
중간
Crawler: 정해진 시간에 등록된 기관을 돌며 공고 · 첨부파일을 모은다. MCP Tool 서버: AI가 실행 중 필요할 때 공식 페이지 조회 · 검색, 그리고 DB 조회 · 벡터 검색을 맡는다(읽기 전용). Checkpoint와 결과 저장은 트랜잭션 때문에 Agent Server가 DB에 직접 쓴다 (Checkpoint는 Agent Server가 자동 관리).
⑥ 서류는 안내만 · 신청은 학생이 직접
중간
필요 서류 확인 → 서류 체크리스트 생성 → 발급 · 준비 방법 안내 → 작성이 필요한 항목은 Drafting Agent가 초안 생성 → 학생 확인 · 다운로드 → 학생이 공식 사이트에서 직접 신청. 학생 개인 증빙서류는 업로드 · 보관 · 검증하지 않는다.
⑦ 데이터 3종류 — 사라지면 서비스가 망가지나?
높음
해야 할 일 → Agent Server run (분석 · 알림) · crawler_jobs (수집). 잠깐의 진행 신호(검색 중 · 30%) → Agent Server 스트리밍, 끊겨도 다시 연결해 이어 받음. 반드시 기억할 상태(추가 질문 · 답변 대기 · 결과) → PostgreSQL · Checkpoint. 학생이 다시 접속하면 API가 DB에서 대기 중인 질문을 조회해 보여준다.
⑧ Vector DB — pgvector로 통합
결정 완료
공고 정보와 embedding은 같은 도메인 데이터이고 규모도 수천~수만 건이라, 별도 Qdrant 대신 PostgreSQL pgvector를 쓴다. 두 DB 간 동기화 문제가 없고, 마감일 · 지역 같은 SQL 조건과 의미 검색을 한 쿼리로 처리한다. 벡터 검색 부하가 따로 커지면 그때 전용 Vector DB로 분리.
⑨ Outbox — run 생성을 잃지 않기
높음
API나 Crawler가 DB 저장 후 Agent Server에 run을 만들기 직전에 죽으면 작업이 사라진다. 그래서 업무 데이터와 outbox를 한 트랜잭션으로 저장하고 Relay가 run을 대신 만든다. Relay가 두 번 보낼 수 있으니 run 생성에 고유 키(멱등성)를 함께 쓴다.
⑩ 멱등성 3단계
높음
API 접수: Idempotency-Key + UNIQUE로 같은 요청 중복 접수 방지. run 생성: outbox id를 고유 키로 써서 같은 run 두 번 생성 방지. 결과 저장: UNIQUE · ON CONFLICT로 중복 결과 방지. 실행이 두 번 일어나도 결과는 한 번만 남게 하는 것.
⑪ Heartbeat · Lease — Agent Server가 담당
직접 구현 X
Worker 생존 확인 · 작업 점유 · 죽은 run 회수는 Agent Server의 실행 관리 기능이 처리한다. 우리가 직접 해야 하는 건 외부 효과(FCM 발송 · S3 저장 · 결과 저장)의 중복 방지뿐. PoC에서 Worker 강제 종료 테스트로 실제 동작을 확인한다.
⑫ 데이터 보존 · 정리
중간
crawler_jobs의 XACK는 삭제가 아니라 완료 확인 — 오래된 메시지는 XTRIM으로 정리. 완료된 오래된 thread · run · Checkpoint는 보존 기간 후 정리, 작성 중 Checkpoint는 유지. Pub/Sub은 저장되지 않음. 운영 전 보존 기간 정책 확정 필요.
⑬ 구현 완료 vs 목표 설계
중간
로컬 랩(구현 완료): Docker Compose · postgres 컨테이너 · MinIO · mock-sites · Mock HTTP 수집 · Mock LLM · Mock 알림 · MCP 도구 3개. 이 그림(목표 설계): EC2 · RDS · S3 · 실제 기관 사이트 · Playwright · 외부 LLM · FCM · MCP 도구 확장. Crawler 해시 조회, MCP의 학생 조회 · 벡터 검색, FCM 발송은 아직 구현 전.
⑭ 단일 EC2의 한계
매우 높음
Worker 2개는 프로세스 장애 대응이지 서버 장애 대응이 아니다. EC2가 꺼지면 Web · API · Redis · Worker · MCP가 함께 멈춘다. RDS · S3의 데이터는 유지되므로 EC2 재기동 후 Checkpoint와 outbox로 재개. 확장 순서: EC2 2대 이상 · 여러 가용 영역 → Redis를 ElastiCache로.
⑮ Redis 손실 대비 — Reconciliation
높음
Relay가 전송 완료로 표시한 뒤 run이나 crawler_jobs가 사라지면 Outbox만으로는 다시 넣어주지 않는다. 그래서 Redis는 AOF 영속화 + 영속 볼륨, 그리고 주기적으로 "DB에는 미완료인데 Agent Server · Redis에 없는 작업"을 찾아 다시 만드는 정합성 재검사를 둔다.
⑯ 알림 처리 주체
높음
알림은 Agent Server의 "알림 발송" 그래프로 실행 — 토큰 500개 묶음 1개 = run 1개. 재시도 · 순서 관리는 Agent Server 큐가 맡아 notify_jobs가 필요 없다. 알림량이 커져 신청서 작업이 밀리면 Notification Worker 컨테이너로 분리.
⑰ Agent Server 전환 조건
매우 높음
① 자체 호스팅 운영 라이선스 · 비용을 공식 문서로 확인 ② 신청서 작성 그래프 하나만 먼저 올려 PoC ③ 기존 장애 테스트 그대로 적용 — 실행 중 Worker 강제 종료 · interrupt 후 서버 재시작 → resume · 같은 요청 2번 → 결과 1번 · 학생 화면까지 스트리밍 ④ 통과하면 전환, 기존 자체 Worker 코드는 그때까지 유지.
⑱ 안정성 2종류
매우 높음
시스템 안정성(서버가 죽어도 작업이 사라지지 않는가) → Agent Server의 검증된 실행 기반에 맡긴다. 서비스 정확성(지원할 수 없는 장학금을 추천하거나 조건을 잘못 안내하지 않는가) → 아낀 시간을 공고 누락 방지 · 자격 조건 추출 정확도 · 근거 검증 · 판정 회귀 테스트에 쓴다.
⑲ 자원 격리 · 백프레셔 (Bulkhead)
높음
API: 요청 수 제한 · 타임아웃 · DB 연결 수 제한. AI: 동시 실행 수 · 학생별 중복 작업 제한. 알림: 묶음 · 발송 속도 제한. 대기열이 너무 길면 신규 요청을 무제한 받지 않고 예상 대기 안내. 알림이 신청 준비를 지연시키는지 테스트 후 Worker Pool 분리.
⑳ 스케줄러 중복 실행 방지
높음
Crawler를 여러 개로 늘리면 내장 스케줄러가 같은 수집 작업을 여러 번 등록할 수 있다. 수집 대상 · 시각으로 만든 고유 키로 중복 등록을 막고, 확장 시 스케줄러를 단일 실행 요소로 분리하거나 분산 잠금으로 한 인스턴스만 등록.
㉑ S3 ↔ DB 정합성
높음
DB 트랜잭션은 S3 업로드까지 묶지 못한다. 원본을 임시 상태로 업로드 → 파일 ID와 공고 버전 기록 → 검증 후 사용 가능 상태로 전환. 실패한 임시 파일 · 고아 객체는 주기적으로 정리, 파일 ID는 내용 해시 기반으로 중복 업로드 방지.
㉒ 외부 호출 실패 정책
높음
LLM · 검색 API · 기관 사이트 호출마다 타임아웃 · 재시도 조건 · 횟수 · 실패 후 상태를 정한다. 일시 네트워크 오류 → 제한된 재시도(Backoff). 429 → 대기 후 재시도. 지속 장애 → Circuit Breaker로 일정 시간 차단. 잘못된 입력 → 재시도 없이 오류. 정보 부족 → 오류가 아니라 학생에게 질문.
㉓ Outbox 장애 테스트 4종
높음
① DB 커밋 직후 FastAPI 종료 ② Relay가 run 생성 요청 직후 종료 ③ Agent Server 실행 중 종료 ④ 결과 저장 직전 같은 작업 재실행. 결과가 DB에 한 번만 남는 것과 외부 LLM · FCM 호출이 한 번만 일어나는 것은 별개의 목표로 각각 검증.
